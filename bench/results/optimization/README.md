## Retained change

The generator knows string literals when compiling a filter. Previously, even a comparison
against `"FR"` loaded `literals[0]` and entered the general `Arrays.equals` range-comparison path.
It now emits the constant length and byte comparisons for literals of up to eight UTF-8 bytes:

```java
length == 2 && bytes[offset] == 70 && bytes[offset + 1] == 82
```

This is a general code-generation rule, not a special case for the benchmark's field names or
`"FR"`. Longer literals use the existing array comparison. It preserves the numeric double
semantics and the complete reading plan: every referenced field is decoded/validated before
evaluating the expression, including when an earlier numeric condition will reject the record.
Empty strings, signed UTF-8 bytes, Unicode, boolean combinations, nonzero slice offsets,
truncation and long fallback literals are tested against materialized Avro or the frozen reader.

The production `AvroCursor.java` is byte-for-byte identical to its recovered version. An
experimental early return for one-byte varints was tested separately and retained only as a
benchmark control: its incremental benefit was much smaller than the literal specialization.

## What explains the improvement

The JIT logs show that **both** generated predicates and their readers are inlined by C2 into
`javaBatch`, and both cursor allocations are eliminated. The old UTF-8 helper and `Arrays.equals`
were also inlined. Consequently, attributing the improvement just to removing a method call
would be wrong: the old code still compiled the general variable-length comparison, including
its range/mismatch machinery, while the specialized code exposes constant bytes directly.

[JIT evidence](jit-evidence.txt) and the [helper details](jit-comparison-helpers.json) document
the distinction. The bounded-slice constructor check remains in both variants. This is causal
evidence at the generator/helper level, not an instruction-by-instruction hardware-counter
attribution of every nanosecond. No claim is made that Java or Classfile inherently executes
faster or slower than Scala staging.

A `final` array reference does not make its elements compile-time constants for the JIT.
Embedding literal bytes in instructions removes that uncertainty. The Scala-generated source
also captures a UTF-8 array and calls a generic comparison, so a comparable specialization is
possible there too. This intervention demonstrates an avoidable cost in the Java prototype;
it does not by itself explain every historical Java/Scala difference.

## Historical reproduction

[The restored sustained run](restored-sustained.json) executes the recovered, unchanged
`SustainedBench` and restored compiled classes. It used one fork, four warmups and three measured
invocations per case as a preliminary reproduction, not the final comparison.

| Distinct records | Scala seconds | Restored Java seconds |
|---:|---:|---:|
| 10,000 | 1.7541 | 1.7625 |
| 100,000 | 4.2442 | 3.6733 |
| 1,000,000 | 4.8064 | 4.5186 |

The historical 2–11% Java penalty is **not reproduced as a stable ratio** after reboot.
Absolute performance, JIT decisions, input layout and host activity can vary between JVMs;
this experiment does not isolate the cause of all that variation. This is why the optimization
is evaluated against a frozen Java implementation in the same caller, across fresh JVMs and
rotated run order, rather than against old Scala numbers.

## Isolating the interventions

[Screening raw results](screen/results.json), two independent JVMs per variant, five warmups
and three measured invocations each, on 10,000 distinct records:

| Change | JVM 1 seconds | JVM 2 seconds |
|---|---:|---:|
| Recovered implementation | 1.7870 | 1.7626 |
| Literal specialization only | 1.4568 | 1.4596 |
| Early-return reader only | 1.7725 | 1.7565 |
| Both candidate changes | 1.4459 | 1.4223 |

All variants allocated about 1.6552 bytes per treated record, including the output buffers.
The string-only intervention reduces the mean time by about 17.8% in this screening run.
The smaller reader effect does not justify an additional production change here.

In this initial screen the `optimized` label meant *both* candidate changes; the final library
keeps only the string change. The `combined` control reproduces that candidate now. Screening
and final source hashes are separately recorded in their manifests. `RestoredAvroFilterCompiler`
and `RestoredAvroCursor` are frozen benchmark-only copies, excluded from the Java library JAR.

## Confirmed measurements

135 measured invocations across 27 fresh JVMs; **every measured invocation lasted over one second**
(minimum 1.392844 s, maximum 4.929032 s). Each row averages 15 invocations in three JVMs per engine.
Times include **300 million record treatments**, with the same output collection in every case.

| Distinct records | Scala (s) | Restored Java (s) | Optimized Java (s) | Java time reduction |
|---:|---:|---:|---:|---:|
| 10,000 | 1.7896 | 1.7629 | 1.4471 | 17.91% |
| 100,000 | 4.0497 | 3.2981 | 3.2893 | 0.27% |
| 1,000,000 | 4.7624 | 4.4809 | 4.2419 | 5.33% |

The small-pool improvement repeats in all three JVM rounds. On the million-record pool the
optimized variant is faster in all three rounds, by approximately 7.2%, 3.9% and 4.9%; the mean
reduction is smaller and should remain scoped to this workload. At 100,000 records the per-round
comparison changes sign and the means are essentially equal: **no convincing improvement is
demonstrated at that size**. The 0.27% mean difference is not a meaningful performance claim.

Compared with Scala, optimized Java uses about 19.1%, 18.8% and 10.9% less time in this campaign.
The restored Java implementation already beats Scala in the larger pools here, so these figures
must not be attributed entirely to the new optimization. The controlled Java-before/after
comparison above isolates the retained change more directly than the cross-engine comparison.

One pass over the pool takes about **48.24 µs / 10k**, **1.096 ms / 100k**, and **14.140 ms / 1m**
with optimized Java. These are derived from long repeated measurements, not separately timed
short invocations. All three engines allocate effectively identical bytes per treated record
at each pool size: approximately 1.6552, 1.3129 and 2.0975 bytes, including the output buffers.

See [all independent JVM means and allocation rates](confirmed/summary.md),
[machine-readable summary](confirmed/summary.json), [raw measurements](confirmed/results.json),
and [run order and source hashes](confirmed/manifest.json). The source hashes still matched
the files at completion; no implementation changes occurred during the campaign.

## Correctness verification

**245 tests pass:** 204 original core tests on restoration, 11 Java-library tests after the
retained change, and 30 benchmark/differential tests. The core implementation is unchanged by
the optimization. The restored complete suite initially had 237 tests.

The checks include materialized-Avro comparisons across shuffled schema layouts, numeric
boundaries and double semantics, short/long/empty/Unicode literals, every changed character,
boolean combinations, slices, framing, concurrent reuse, 20,000 random malformed slices, and
the existing random int64/truncation/overflow reader checks. The benchmark setup independently
validates retained offsets and original record identities.

Logs: [restoration](restore-validation.log), [final affected suites](final-validation.log).

The [separate packaged-JAR consumer](embedding-smoke.log) also passes. It is compiled with
`javac --release 24` against the JAR and production dependencies only, then run on JDK 25.
Scala, the staging compiler, JMH and benchmark controls are absent from that classpath and
the packaged artifact. The JAR is **25,892 bytes**, has Java-24 class version 68, and its POM
declares Apache Avro as the only direct production dependency. Java 24 runtime execution
was not tested; all executions here use the installed JDK 25.

## Protocol and limits

- Apple M4 Max, 64 GiB RAM; Temurin 25.0.3+9-LTS, Scala 3.8.4, JMH 1.37.
- One benchmark thread, fixed 2 GiB heap, default JVM compilation flags, compiler blackhole,
  JMH GC profiler. No profiling flags, forced inlining, or disabled validation in the final run.
- `OptimizationBench` preserves the recovered sustained benchmark's iteration and output
  collection. Scala, restored Java and optimized Java run in separate JVMs. Each case has
  six warmup invocations and five measured invocations, repeated in three fresh JVMs.
- The runner rotates engine order between rounds and dataset sizes; only one benchmark JVM
  runs at a time. No builds or tests run concurrently with the measurement campaign.
- Each invocation performs exactly **300 million record treatments** by replaying a pool
  of 10,000, 100,000 or 1,000,000 distinct records. Every measured invocation must last at least
  one second. These are not 300 million distinct messages. Generation, filter compilation,
  loading and correctness validation occur before timing.
- Both implementations retain the same original records in fresh Scala `ArrayBuffer`s.
  Setup checks every offset and record identity against the source events; each measured
  invocation consumes its buffers and verifies the aggregate result count.
- The larger pools change memory locality as well as iteration and output allocation.
  Hardware cache-miss counters were not collected, so locality is a plausible explanation
  for attenuated CPU savings at larger sizes, not an isolated causal finding.
- This is an interactive workstation with other applications running, not a reserved host.
  Independent JVM means are reported, including variation; measured iterations within a JVM
  are not presented as independent hosts. Small differences should not be overinterpreted.
- Scope: one scalar Avro filter and schema, tiny in-memory records, a monomorphic hot call.
  These are not Kafka end-to-end throughput results. Larger filters, longer literals,
  mixed-schema dispatch, and different payload distributions require their own measurements.

## Reproduce

From the repository root with JDK 24+ (these runs use JDK 25):

```sh
sbt 'classfile/test' 'core/test' 'bench/test' 'bench/Jmh/compile'
python3 bench/scripts/run_optimization.py --output bench/results/optimization/recheck
python3 bench/scripts/summarize_optimization.py bench/results/optimization/recheck
```

Use a new output directory for each campaign; the runner refuses to overwrite an existing one.
It records exact commands, JVM version, source hashes, all warmups, per-invocation measurements
and GC data. It fails if a JVM fails or a measured invocation is shorter than one second.

To repeat the intervention controls without the large pools:

```sh
python3 bench/scripts/run_optimization.py --sizes 10000 \
  --engines restored literalOnly cursorOnly combined --forks 2 --warmup 5 --iterations 3 \
  --output bench/results/optimization/control-recheck
```

Build the embeddable library with:

```sh
sbt 'classfile/packageBin' 'classfile/packageSrc' 'classfile/makePom'
```

Verify the packaged dependency closure independently:

```sh
sbt 'show classfile/Runtime/fullClasspath'
python3 bench/scripts/check_library.py
```

The library requires no Scala, staging compiler or JMH runtime dependency. Apache Avro remains
its only direct production dependency. See [the library API](../../../classfile/README.md).
