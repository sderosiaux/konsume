# Why the original Java prototype was slower

Investigation on 2026-11-18, Apple M4 Max, Temurin 25.0.3, JMH 1.37. Same 10,000 Avro records and filter as the initial experiment; 1,521 original records retained.

The original result measured differences in the **Avro decoder implementation and calling context**, not a demonstrated intrinsic penalty of the Class-File API. Generation and class loading were outside the runtime measurement. Replacing only the decoder behind the generated bytecode substantially reduced the gap. A safe decoder-loop improvement is now in the Java library.

## Current result in the original benchmark

All rows below use `ClassfileBench`, with 8 × 1 s warmup, 5 × 1 s measurement, 2 JVM forks, one thread, and the GC profiler. Lower is better. ± is JMH's 99.9% confidence interval half-width.

| Implementation | µs / 10,000 records | Allocated bytes / batch |
|---|---:|---:|
| Corrected Java Classfile | 60.375 ± 1.194 | 16,552 |
| Handwritten Java using the corrected reader | 60.319 ± 0.781 | 16,552 |
| Existing Scala staged function | 59.077 ± 0.486 | 16,552 |

The generated Java and handwritten Java results remain close. Java and Scala are now close on this workload and their reported intervals overlap. This is not a formal proof of equal performance across workloads. The historical 21% execution gap should not be treated as a property of Classfile, or as the performance of the current JAR.

## Hypotheses checked

| Hypothesis | Experiment and observation | Finding |
|---|---|---|
| Class loading on the hot path | All measured `class.load.norm` values in the controlled matrix were exactly zero. Compilation/instantiation happen in trial setup. | No repeated loading in the measured path. |
| Hidden-class loading makes execution slower | Load **identical bytes** as a hidden class and as a named class: 77.717 ± 2.443 vs 78.118 ± 1.924 µs in the same adapter harness. | No measurable penalty for the hidden loading mode in this experiment. |
| Insufficient warmup / cold start | Original benchmark repeated with 8 s warmup, 8 s measurement, 3 fresh JVM forks: Java 67.979 ± 0.459, Scala 58.109 ± 0.639 µs. | The original gap persists after extended warmup. |
| Reflection or interpreter dispatch remains | C2 logs show the generated `test`, `readLength`, `readLong`, cursor constructor and UTF-8 comparison inlined into the batch loop. | The original predicate executes optimized code, not repeated reflective invocation or interpretation. |
| More allocations in the original Java variant | About 16.5 KB per batch in both engines; C2 explicitly records elimination of the original cursor allocation. | Allocation does not explain the original 21% gap. |
| Decoder implementation | Keep generated predicate, literals, loading mode and caller unchanged; substitute cursor implementations. See the next table. | Main demonstrated source of the execution difference. |
| Benchmark/caller structure | Direct predicate calls and a common Scala `Function2` adapter produce different absolute timings. | The first comparison was not an isolated language/compiler comparison. Calling context affects JIT optimization. |

There was some background JIT activity during measurement; it was not literally zero. The important filter methods had C2 compilations and successful inlining, and the extended-warmup result was stable. The evidence does not support cold start as the cause of the persistent gap.

## Controlled decoder substitutions

These rows all come from `PredicateInvestigationBench`, using the same direct predicate call, same bytecode template, same output buffer and data. Only one backend is exercised in each fork, including setup validation. Settings: 8 × 1 s warmup, 5 × 1 s measurement, 2 forks, `gc`, `cl` and `comp` profilers.

| Decoder behind the generated predicate | µs / batch | Allocated bytes / batch |
|---|---:|---:|
| Original Java general varint loop | 71.979 ± 1.203 | 16,553 |
| Java with the first byte outside the loop, same validation | 66.966 ± 1.517 | 16,553 |
| The actual Scala Avro cursor | 59.638 ± 1.024 | 16,553 |
| Experimental fast path calling a separate slow helper | 94.062 ± 10.179 | 256,553 |

Replacing only the cursor brings the generated Classfile predicate to roughly the Scala engine's range. This strongly localizes the issue to the decoder/support code, rather than bytecode generation or loading.

The dataset contains **28,022 one-byte varints out of 30,000 reads (93.4%)**: every name length and country length, plus 8,022 of the ages. The original Java decoder began with a general `for` loop and shift/overflow/slice checks. Scala reads the first byte before entering its continuation loop. The retained change expresses that common case directly, in one method, while keeping the Java slice boundary and invalid tenth-byte checks.

This is a source/bytecode-shape result backed by measurements, not an instruction-by-instruction assembly attribution. The experiments do not justify assigning every remaining nanosecond to one particular check.

## Additional controls and rejected explanations

- A peeled Java reader bounded only by the array measured 64.381 ± 1.452 µs; the slice-checked peeled control in that run measured 65.667 ± 3.137. Their intervals overlap. Removing explicit slice checks alone is not a demonstrated explanation for the whole residual difference, and the weakened contract was **not** shipped.
- Flattening the literal storage from `byte[][]` to a direct `byte[]` field did not provide a useful gain: original decoder 73.917 ± 1.325, peeled decoder 67.489 ± 1.314, Scala decoder 59.730 ± 0.925 µs. This change was not shipped.
- The adapter harness's absolute timings differ from direct-predicate and original-harness timings. Compare rows within a single table/JSON run; do not add deltas from different harnesses into an exact cost breakdown.

## A concrete JIT failure in the rejected fast-path experiment

The split fast/slow experiment looked simpler on the frequent path but made the result worse. The C2 log says:

```text
FastAvroCursor.readLong       inline_success  inline (hot)
FastAvroCursor.readLongSlow   inline_fail     too big
Eliminated allocations: none
```

The cursor now escapes into a non-inlined helper. The GC profiler reports about **240,000 additional bytes per 10,000-record batch**, exactly 24 bytes per record, consistent with one allocated cursor. In the original, peeled and Scala-reader variants C2 explicitly eliminates the cursor allocation.

As a causal control, forcing only that helper to inline with `-XX:CompileCommand=inline,konsume.classfile.FastAvroCursor::readLongSlow` restores allocation to **16,552 bytes per batch**, with a diagnostic timing of 68.805 µs. This was a single-fork diagnostic, not a new production throughput claim. The delivered library requires **no special JVM flags** and keeps its loop in one method.

See extracted JIT evidence (`jit-evidence.txt`), structured evidence and raw-log hashes (`jit-evidence.json`), and the [extraction script](../../scripts/summarize_jit.py). The complete local logs are `/private/tmp/konsume-jit-pid76205.xml`, `...pid76441.xml`, `...pid76722.xml` and `...pid77114.xml`.

## Retained change and verification

- [AvroCursor.readLong](../../../classfile/src/main/java/konsume/classfile/AvroCursor.java) reads the first byte before its continuation loop. Bounds checking, rejection of truncated/overflowing varints, and the public API remain intact.
- The old reader is frozen as `BaselineAvroCursor` in the **benchmark module only**, so before/after comparisons remain reproducible.
- A separate final three-fork paired run measured 77.961 ± 1.370 µs for the frozen reader versus 64.198 ± 0.669 µs for the current one. These are the direct-predicate harness values, not the original-harness table above.
- **235 tests passed**: 204 original core tests, 9 Java-library tests, 22 benchmark/differential tests. Added decoder checks cover 10,000 random int64 values, boundaries, every truncation of selected encodings, invalid tenth bytes and 10,000 random byte slices, comparing the old and new readers.
- The rebuilt Java-24-targeted JAR was compiled against and run from a separate Java consumer, with no Scala, staging compiler or JMH on its classpath. Experimental readers and benchmark classes are absent from the JAR.
- Current artifact: `classfile/target/konsume-classfile-0.1.0-SNAPSHOT.jar`, **25,702 bytes**. Source JAR and Maven POM are alongside it.

The public library still supports its documented scalar Avro-filter subset. Measurements cover one small filter, one writer schema, in-memory input and a repeated call pattern; mixed-schema applications or different data distributions can optimize differently.
